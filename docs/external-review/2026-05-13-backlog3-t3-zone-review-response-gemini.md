## 7.1 Group α 질문 (AR-3 + PC-4 T3 sub) — 6 질문

**Q1. AR-3 통합 결정 영역 중 최선 옵션은?**
**판정**: **(g) (a)+(b)+(c)+(d) 통합**
**근거**:

* **Provider Liquidity**: 특정 벤더에 의존하지 않는 GitHub 표준 기능이므로 유동성 보전에 유리합니다.
* **Hermes ≠ root of trust**: Hermes가 생성한 코드가 직접 main에 머지되는 것을 방지하고, 반드시 CI와 서명 검증을 거치게 함으로써 "검증 대상"으로서의 지위를 확고히 합니다.
* **1인 개발자 부담**: 초기 설정 오버헤드는 있으나, "에이전트가 잘못하는 것이 불가능하게 만든다"는 메타-슬로건에 가장 부합합니다. 1인 개발 환경에서도 자기 통제(Self-discipline)를 시스템적으로 강제하는 효과가 큽니다.

**Q2. PC-4 T3 sub 결정 영역 중 최선 옵션 조합은?**
**판정**: `fail_fast: true` + `commit-msg/pre-push` 도입 + `--no-verify` 차단 정책(서버사이드 결합)
**근거**:

* **Friction 최소화**: `fail_fast`를 통해 첫 번째 오류에서 즉시 중단하여 피드백 루프를 단축합니다.
* **우회 최소화**: 로컬에서의 `pre-commit`은 우회가 쉬우므로, 반드시 AR-3(Q1)의 branch protection과 결합하여 서버사이드에서 최종 차단해야 합니다.

**Q3. AR-3 × PC-4 T3 sub 결합 효과 평가**
**판정**: **결합 형태가 유일하게 유효한 차단책임**
**근거**: 로컬(PC-4)은 개발 속도를 위한 1차 필터이며, 서버(AR-3)는 무결성을 위한 최종 게이트입니다. `pre-commit` 단독으로는 `--no-verify`를 막을 수 없으며, branch protection 단독으로는 개발 과정의 실시간 피드백이 부족합니다. 결합 시 우회 가능성은 "GitHub 관리자 권한을 이용한 강제 푸시" 외에는 차단됩니다.

**Q4. 외부 contributor / fork PR 정책 최선 옵션**
**판정**: **default 정책 유지 (secrets = fork PR 자동 차단)**
**근거**: 1인 개발자 환경에서 외부 기여는 예외적인 케이스입니다. `pull_request_target`은 보안 숙련도가 매우 높지 않으면 Secret 유출의 주요 경로가 됩니다. 템플릿의 안전성을 우선한다면 보수적인 기본값을 유지하고, 필요 시에만 개별 승인하는 것이 타당합니다.

**Q5. commit signing 의무화 시점 및 운영 영향**
**판정**: **MVP-6 (Operational Readiness) 발효 시 권고**
**근거**: 현 시점(MVP-1)에서 의무화하기에는 1인 개발자의 키 관리 부담과 환경 구성(GPG/SSH) 비용이 안전 이득에 비해 높습니다. 에이전트 자동 커밋과의 연동(Sign-off vs Signing) 이슈가 해결되는 시점인 MVP-6가 적절합니다.

**Q6. 본 Group α 합의가 진입 부적합인 시점/영역**
**판정**: **Backlog #6 (Runtime enforcement) 미진입 시 진입 부적합**
**근거**: 실제 차단 로직(Implementation)이 준비되지 않은 상태에서 정책(T3)만 선언하는 것은 "수단 ↔ 목적 분리" 원칙에 어긋납니다. 실행 수단이 확보된 직후 진입해야 합니다.

## 7.2 Group β 질문 (T-5 (β) + Tier-2/3 일반) — 6 질문

**Q7. Tier-2/3 catalog 자동 확장 정책 일반 최선 옵션**
**판정**: **YAML 기반 자체 catalog 유지 + 수동 트리거 기반 업데이트**
**근거**: 자동 동기화는 편리하나 FP(False Positive) 발생 시 제어가 어렵습니다. 1인 개발 환경에서는 "명시적 관리"가 단일 source-of-truth 보존에 유리합니다. 확장 프로세스는 `Implementation Evidence PASS`를 통해 실측 데이터(정탐/오탐률)가 확인된 후 가동해야 합니다.

**Q8. T-5 (β) 권고 vendor 확장 범위**
**판정**: **Tier-2 확장(Mistral, AI21, HuggingFace 포함) / Tier-3 도입 보류**
**근거**: Mistral과 HuggingFace는 이미 실무에서 활발히 사용되므로 유동성 확보를 위해 포함이 시급합니다. 반면, Tier-3(비주류/Legacy)는 관리 비용 대비 실익이 적고 FP 위험만 높이므로 보류를 권고합니다.

**Q9. LiteLLM 자동 동기화 vs 자체 유지**
**판정**: **자체 catalog 유지 (LiteLLM은 참조용)**
**근거**: LiteLLM 의존은 공급망 위험을 초래합니다. 벤더의 이름 변경이나 deprecated 대응은 템플릿의 핵심 정책 영역이므로, 외부 라이브러리에 위임하기보다 ADR-011의 "단일 source-of-truth" 하에 직접 관리하는 것이 안전합니다.

**Q10. provider lock-in 강화 위험 역효과 평가**
**판정**: **실재하는 위험 (강도: HIGH)**
**근거**: 차단 카탈로그가 엄격할수록 새로운 벤더를 시도할 때의 허들이 높아집니다. 이는 `Provider Liquidity 5-way`를 약화시킬 수 있습니다. **완화 방법**: "Sandboxed Tier" (T1 영역)를 두어 신규 벤더를 한시적으로 허용하고, 검증 후 카탈로그에 편입시키는 유연함이 필요합니다.

**Q11. GP-3 / GP-5 확장 정책 통합 vs 분리**
**판정**: **정책 프레임워크 통합 / 구현 분리**
**근거**: "무엇을 신뢰하지 않을 것인가"에 대한 상위 정책(Tier 정의, 확장 기준)은 통합 관리하되, 기술적 구현(Secret 탐지 vs Provider 차단)은 개별 도구의 특성에 맞춰 분리하는 것이 유지보수에 용이합니다. MVP-2 이후 Evidence 기반 진입을 권고합니다.

**Q12. 본 Group β 합의가 진입 부적합인 시점/영역**
**판정**: **Implementation Evidence PASS 미발효 시 진입 부적합**
**근거**: 카탈로그 확장은 오탐(FP)으로 인해 개발 경험을 심각하게 저해할 수 있습니다. 실제 프로젝트 코드셋에서의 오탐 테스트 결과 없이 T3 정책을 확정하는 것은 위험합니다.

## 7.3 Group γ 질문 (C-5b ST-1 + Vault HSM ST-4) — 6 질문

**Q13. C-5b ST-1 (Hermes upstream 변경) 최선 옵션**
**판정**: **entrypoint 내 `chmod 600` 검증 로직 추가 (실패 시 즉시 중지)**
**근거**: Hermes를 root of trust로 보지 않으므로, 실행 환경 스스로 권한 무결성을 검증하는 것은 타당합니다. 다만, upstream 직접 수정보다는 Dockerfile layer에서의 추가 검증이 1인 개발자의 관리 부담을 줄이는 대안이 될 수 있습니다.

**Q14. Vault HSM ST-4 최선 옵션 및 의미**
**판정**: **현 시점 도입 보류 (MVP-6 이후 재검토)**
**근거**: 1인 개발자 single-host 환경에서 Vault HSM은 오버엔지니어링일 가능성이 높습니다. SPOF 의도적 수용(ADR-012) 원칙과 충돌하며, 인프라 비용과 관리 복잡도만 증가시킵니다. "메타-템플릿"으로서의 상징성은 있으나 실질적 이득이 낮습니다.

**Q15. ST-1 ~ ST-4 통합 정책**
**판정**: **Defense in depth (ST-1/2/3 우선) > 단일 source (ST-4 후순위)**
**근거**: 파일 시스템 권한(ST-1)과 Docker Secret(ST-3)은 저비용 고효율 보안책입니다. ST-4는 이 모든 것이 갖춰진 후의 최종 단계로 설정하는 것이 "수단-목적 분리"에 부합합니다.

**Q16. ST-4 진입 시점**
**판정**: **MVP-6 (Operational Readiness) 이후**
**근거**: Multi-host 인프라가 전제되지 않은 single-host에서의 HSM은 논리적 격리 수준에 그칩니다. 인프라 준비가 완료된 시점에 진입하는 것이 옳습니다.

**Q17. Hermes upstream 변경 vs PMO 격상 경계**
**판정**: **PMO 격상과 동시 또는 이후 진행**
**근거**: Upstream 변경은 시스템의 근간을 건드리는 작업입니다. 이는 Hermes를 "단순 도구"에서 "PMO 수준의 신뢰 대상"으로 격상하는 논의와 병행되어야 하며, root of trust 침범 위험을 방지하기 위한 외부 LLM 2인 이상의 교차 검증이 필수적입니다.

**Q18. Operational Readiness PASS 경계**
**판정**: **Vault HSM 도입 전 필수 조건**
**근거**: 1인 개발 환경에서 Operational Readiness는 "운영 가능성"의 증명입니다. Vault와 같은 복잡한 도구를 도입하기 전, 운영 가동성을 확보하는 Backlog #7이 선행되어야 합니다.

## 7.4 종합 판정 질문 (#19)

**Q19. 최종 판정**
**결정**: **(C) PARTIAL — Group α + β 진입 승인 / Group γ 보류**

**판정 근거 및 우선순위**:

1. **Group α (우선순위 1)**: 가장 즉각적인 보안 이득을 제공하며, 1인 개발 환경에서도 GitHub 기본 기능을 활용해 저비용으로 구축 가능합니다. "우회 불가능한 시스템" 구축의 초석입니다.
2. **Group β (우선순위 2)**: 유동성 확보를 위해 필요하나, **Implementation Evidence PASS** 충족을 조건으로 승인합니다(APPROVE WITH CONDITIONS). 오탐에 대한 실측 데이터가 우선입니다.
3. **Group γ (보류)**: 현재의 single-host 1인 개발 환경에서 Vault HSM 도입은 목적에 비해 수단이 지나치게 무겁습니다. 특히 Hermes upstream 변경은 PMO 격상 논의와 맞물려야 하므로, MVP-6 이후로 미루는 것이 시스템 안정성 측면에서 유리합니다.

**그룹 분리 적절성**:

* 현재의 3그룹 분리(α, β, γ)는 책무 영역이 명확히 구분되어 있어 적절합니다. 특히 α와 γ를 분리한 것은 "환경 enforcement"와 "Secret 인프라"의 복잡도 차이를 잘 반영하고 있습니다.

**본 prep brief의 결함/누락**:

* **에이전트 권한 위임**: AR-3 진입 시, AI 에이전트(Claude Code 등)가 PR을 생성하고 체크를 통과하기 위한 **봇 계정/App의 권한 범위**와 **서명 방식**에 대한 구체적인 가이드가 누락되었습니다.
* **FP 복구 프로세스**: Group β에서 오탐으로 인해 핵심 벤더 접근이 차단되었을 때, 긴급히 이를 bypass 할 수 있는 "비상 탈출구" 정책(ADR-011 위반 없이)에 대한 정의가 필요합니다.
