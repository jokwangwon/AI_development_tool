**종합 결론: CONDITIONAL-PASS**

프라이데이 신설은 자기모순이라기보다 “자가진화 연구용 샌드박스”로는 정당합니다. 다만 현재 표현은 AGI, Provider Liquidity, 자가진화라는 단어의 범위가 넓어 오해 가능성이 큽니다. 통과 조건은 프라이데이를 “로컬 실행 AI를 개선하기 위한 격리된 실험 루프”로 재정의하고, MVP-0의 진화 대상을 좁히는 것입니다.

## 1. 구조 모순 여부

자기모순은 아닙니다.  
Claude Code가 “훈련/개선 오케스트레이터”이고, 프라이데이 런타임이 “교체 가능한 로컬 추론 시스템”이라면 이는 부트스트랩 패턴입니다.

다만 Provider Liquidity를 다음처럼 구분해야 합니다.

- **런타임 Provider Liquidity**: 프라이데이 배포 추론은 로컬 모델이며 교체 가능하다. 이 주장은 성립.
- **진화 엔진 Provider Liquidity**: Claude Code `/loop`에 의존한다면 성립하지 않음.
- **전체 시스템 Provider Liquidity**: 현재는 부분 성립. Claude가 빠지면 진화 속도나 품질이 급락할 수 있음.

따라서 표어는 괜찮지만 헌법 문구로는 위험합니다.

권장 표현:

> 프라이데이는 런타임 추론에서 Provider Liquidity를 유지한다. 초기 진화 오케스트레이션은 Claude Code를 부트스트랩 엔진으로 사용하되, 산출물은 독립 검증 가능하고 장기적으로 교체 가능해야 한다.

핵심 조건은 Claude가 만든 개선안이 **프라이데이의 root of trust가 되지 않는 것**입니다. Claude는 후보 생성자이지 권위자가 아니어야 합니다.

## 2. AGI 동반 성장 비전과 현실 구현의 갭

정직한 기대치는 “AGI”가 아니라 다음에 가깝습니다.

- 사용자 선호, 프로젝트 맥락, 반복 작업 패턴을 누적하는 개인화 에이전트
- 로컬 LLM 기반의 장기 메모리/도구 사용/자기평가 루프 실험체
- 자율적으로 코드를 적용하는 존재가 아니라, 자기 개선 후보를 만들고 검증 리포트를 쌓는 시스템
- 특정 사용자와 특정 워크플로에 대해 점진적으로 더 유용해지는 “개인 AI 동반자 프로토타입”

1인 개발자 + GB10 + 루프 하네스로 가능한 것은 **범용 AGI의 탄생**이 아니라 **개인 운영 환경에 적응하는 지속학습형 에이전트**입니다.

권장 프레이밍:

> 프라이데이는 AGI를 주장하지 않는다. 프라이데이는 AGI적 속성인 지속성, 자기반성, 도구 사용, 장기 기억, 사용자 적응을 개인 로컬 환경에서 실험하는 동반 지능 프로토타입이다.

이렇게 두면 비전은 유지하면서 over-claim을 피할 수 있습니다.

## 3. 자가진화 대상의 명확성

자가진화 대상을 한 번에 열면 위험합니다.

대상별 위험도는 대략 이렇습니다.

- **메모리**: 낮음에서 중간. 가장 실용적.
- **프롬프트**: 중간. 행동 변화가 크지만 rollback 가능.
- **도구 설정**: 중간에서 높음. 권한 확대 위험.
- **정책**: 높음. invariant 침범 가능.
- **자기 코드**: 매우 높음. 검증 비용과 보안 위험이 큼.

MVP-0에서 가장 실질 가치 있는 진화 대상은 **메모리 정책/사용자 모델**입니다.

구체적으로는:

> 프라이데이는 대화와 작업 결과에서 “사용자 선호, 프로젝트 규칙, 반복 패턴, 실패 사례”를 추출해 구조화된 메모리 후보를 만들고, 사용자가 승인한 항목만 장기 메모리에 반영한다.

이것이 좋은 이유는 명확합니다.

- 개인 AI 동반 성장 비전에 가장 직접적으로 연결됨
- 코드 변경 없이도 체감 가치가 있음
- rollback이 쉬움
- 보안 검토가 비교적 단순함
- 자비스와 분리해도 독립적으로 발전 가능함

MVP-0에서 자기 코드 수정은 금지하는 편이 맞습니다. 프롬프트 자동 변경도 바로 열지 말고 “프롬프트 개선 제안서 생성”까지만 두는 것이 적절합니다.

## 4. 격리 설계의 허점

5-layer 격리는 방향은 좋지만, 누락된 우회 경로가 있습니다.

가장 큰 허점은 **같은 OS 계정**입니다. 같은 UID라면 ACL, workdir prefix, git branch는 심리적/구조적 경계일 뿐 완전한 보안 경계가 아닙니다. 프로세스 권한, 홈 디렉토리, SSH 키, shell history, Claude 설정, git credential, Ollama 캐시를 공유할 가능성이 큽니다.

주의할 우회 경로:

- 같은 사용자 계정의 `~/.ssh`, `~/.gitconfig`, credential helper 접근
- Claude Code 세션/설정/토큰/작업 히스토리 공유
- 같은 Ollama 모델 저장소 또는 캐시 접근
- 같은 디스크에서 symlink, hardlink, bind mount, temp directory 경유
- `/tmp`, shell history, logs를 통한 정보 누출
- git remote credential 공유
- tmux 세션 이름 충돌 또는 attach 가능성
- 포트 충돌 및 localhost 서비스 접근
- 환경변수 유출, 특히 API key
- Landlock 적용 전 초기화 코드가 파일을 여는 TOCTOU성 문제
- 백업/인덱서/검색 도구가 양쪽 디렉토리를 동시에 스캔하는 문제

권장 보강:

- 프라이데이는 별도 Unix user로 실행
- 별도 `$HOME`, 별도 `XDG_*`, 별도 Ollama home
- systemd unit 또는 container로 CPU/GPU/메모리 제한
- 네트워크 egress 정책 분리
- Claude Code 작업 디렉토리와 config 분리
- allowlist 기반 파일 접근 테스트를 CI처럼 반복
- symlink escape 테스트 추가

Landlock은 좋은 방어층이지만 “같은 계정의 실수”를 모두 막는 주 경계로 보면 안 됩니다.

## 5. 비례성

현재 설계는 1인 개인 프로젝트 기준으로는 무겁습니다. 그러나 “자가진화”와 “기존 prod 자비스 보호”가 목표라면 과잉이라고만 보기는 어렵습니다.

다만 경량화할 수 있습니다.

유지해야 하는 것:

- 자비스/프라이데이 repo 또는 worktree 분리
- 별도 Ollama endpoint
- 별도 메모리 디렉토리
- rollback trigger
- 프라이데이 결과가 자비스 변경 제안도 못 하게 하는 권위 분리

경량화 가능한 것:

- 다중 합의/fan-out은 MVP-0에서 상시 적용하지 않아도 됨
- 적대적 검증은 코드/정책 변경이 있을 때만 적용
- 5-layer를 매번 수동 점검하지 말고 smoke test로 자동화
- 브랜치 분리보다 별도 repo + 별도 Unix user가 더 단순하고 강함
- 초기에는 “자가 코드 수정 금지”로 두면 거버넌스 부담이 크게 줄어듦

즉, 안전 결과를 유지하면서 더 단순한 MVP는 다음입니다.

> 별도 Unix user + 별도 repo + 별도 Ollama + 별도 memory dir + 네트워크/자원 제한 + 메모리 진화만 허용.

이 조합이 현재의 복잡한 다중 합의보다 실제 안전성 대비 효율이 좋습니다.
