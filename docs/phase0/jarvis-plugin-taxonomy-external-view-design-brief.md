# 설계 brief — 플러그인 taxonomy 신설: 탑재형 vs 외부 관제형 (전권 통제 + 리스크 비례 게이트)

> **상태**: v2.1 (사용자 결정 반영: 전권 통제 + 리스크 비례 게이트 + **적용 범위 = 자비스 도움 프로젝트 한정** · 검토 대기) · **출처**: 127 세션 "이 플러그인을 다시 생각해보자" 재고
> **상위**: `jarvis-plugin-architecture-design-brief.md` v2 (탑재형 정책 — 그대로 유효)
> **핵심 명제**: **플러그인은 한 종류가 아니다.** "자비스에 *탑재*하는 것"과 "외부에서
> 독립 운용하고 자비스에서 *관제(보기 + 제어)*하는 것"은 다른 정책이 필요하다.
> **사용자 결정(127)**: 자비스 = **전권 통제**(넓은 범위) + 게이트는 **리스크 비례**(가역=자율, 비가역=승인).
> **사용자 결정(127, 비협상)**: 외부 관제형의 대상 = **자비스가 (워커로) 구축을 도운 프로젝트에 한정**. 임의 제3자 ❌ (§1.5).
> **다음 단계**: v2 검토 → **풀 3+1 합의**(외부 시스템 write/control = 보안 표면 ↑). **자동 진입 0**.

## 0. 이 brief가 생긴 이유 (127 재고)

세션 120~126에서 플러그인 아키텍처 dogfooding 매트릭스를 채웠다(clock·measure_log·
port_probe·tts). 그런데 **만든 플러그인이 전부 검증/데모용**이었고, "그래서 진짜 뭘 끼울
건데?"에 답이 없었다. 사용자에게 이를 되물으니 — 플러그인을 **두 종류로 구분**하고 있었고,
나아가 외부형에 대해 **"전권 통제 자비스"** 비전을 명시했다.

> 사용자 발화(요약):
> 1. *"탑재하고 싶은 건 현 플러그인 정책에 맞지만, 별도 테스트(예: 음성 모델)는 다른 레포·
>    다른 시스템에서 하고, 자비스에선 그걸 좀 더 쉽게 *보고* 싶을 뿐."* → **외부형 발견**
> 2. *"관제탑에서 간단한 리터치는 못 하나? 자비스가 실제 자비스처럼 *전면적으로 전체 통제
>    권한*을 다 가졌으면 좋겠다."* → **관제 = 보기만이 아니라 보기 + 제어**

→ 현 아키텍처는 **한 종류(탑재형)만** 상정했다. 두 번째 종류(외부 관제형)가 빠져 있었고,
그 자리에 **잘못된 첫 사례(TTS)** 가 끼워졌다(§3).

## 1. 핵심 발견 — 플러그인의 두 종류 (taxonomy)

| 축 | **A. 탑재형 (Embedded)** | **B. 외부 관제형 (External / Federated)** |
|---|---|---|
| 정체 | 자비스의 *기능*이 된다 | 자비스의 일부가 **아니다** — 독립 시스템 |
| **적용 범위** | (자비스 자신) | ⭐ **자비스가 (워커로) 구축을 도운 프로젝트에 한정** — 임의 제3자 ❌ (provenance 기반, §1.5) |
| 사는 곳 | 자비스 트리(`jarvis_hud/plugins/<name>/`)에 흡수 | **다른 repo / 다른 시스템 / 별도 브랜치** |
| 실행 | 자비스 본체 프로세스 *안* (동적 import, in-process) | **외부에서 독립 실행** (자비스와 별개 생명주기) |
| git 모델 | B복사 게이트로 메인 트리 통합 | 자비스가 **소유하지 않음** (외부 버전관리) |
| 자비스 관계 | 호스트 — 흡수·통합·실행 | **관제탑 — 보기 + 제어** (리터치~제어, 리스크 비례 게이트 §3.5) |
| 권한/포트 | `select_ports` 최소권한 주입(in-process 신뢰경계) | 외부 = 자비스 신뢰경계 *밖* — **연결 자격증명 + 리스크 게이트**로 제어 |
| 현 구현 | ✅ 존재 (120~126 dogfood 완료) | ❌ **부재 — 본 brief가 신규 정의** |
| 예시 | 계산기, 자비스 기능 확장 | **음성(TTS) 모델 테스트, 이미지 생성 비교** |

**핵심**: 두 종류는 **신뢰 경계·격리 수준·git 소유권**이 근본적으로 다르다. A는 "자비스 안으로
들어오는" 것이라 B복사+포트+재시작 게이트가 정당하다. B는 "자비스 밖에 머무는" 것이라 흡수
게이트는 과하지만 — 대신 **외부 시스템을 만지는 제어 채널 + 리스크 비례 게이트**가 필요하다(§3.5).

## 1.5 적용 범위 제약 — "자비스가 도와 만든 프로젝트"에 한정 (127, 비협상) ★

외부 관제형(B)의 **읽기측·제어측 모두**, 그 대상은 **자비스가 (워커를 통해) 구축에 관여한
프로젝트에 한정**된다. 임의의 제3자 외부 시스템을 관제 대상으로 받지 않는다.

- **왜 (provenance/출처 기반 신뢰)**: 자비스가 만든 프로젝트는 자비스가 그 구조·코드·제어
  표면을 이미 안다. 모르는 제3자 시스템엔 관제 권한을 줄 근거가 없다. 이는 원래 동기 (B)
  *워커 산출물 반영*(`[[project_jarvis_output_application_gap]]`)의 자연스러운 연장 — 워커가
  격리 work/ 에서 만든 산출물이 별도 프로젝트(repo/브랜치)로 독립한 뒤에도 자비스가 계속
  *관제*하는 흐름. 즉 외부 관제형 = **워커 산출물의 생애주기 연장**.
- **보안 함의 (양면 — 잘 생각할 부분)**:
  - (완화) 제3자 임의 시스템 배제 → SSRF·악의적 외부 데이터·임의 자격증명 표면이 크게 줄어든다.
    합의 **U-2**(외부 본인 작품 여부)가 이 제약으로 **해소** — C-β(외부가 자기 자격 보유)가 자연스럽다.
  - (게이트 유지 필수) **"자비스가 도와 만든" ≠ "신뢰됨".** 워커는 통제된 자식(untrusted,
    `[[project_jarvis_controlled_child_then_friday]]`), 산출물은 오염 가능(2차 injection 등).
    범위가 좁다고 §3.5 리스크 게이트를 없애면 안 된다. **좁힘 ≠ 신뢰.**
- **경계 식별 (신규 갈림길 G7)**: "도와 만든 프로젝트"를 어떻게 *결정적으로* 식별하나 —
  자비스가 구축 시 provenance 표식을 레지스트리에 기록(자비스-origin), 사람이 임의 URL 을
  관제 대상으로 등록하려면 명시 게이트. **fail-closed: origin 불명 = 관제 대상 아님.**

## 2. 현 구조 진단 (외부 관제형 관점)

| 영역 | 상태 | 외부형에 대한 함의 |
|---|---|---|
| plugin_install (B복사) | work/ → `jarvis_hud/plugins/` 안전 복사 | 외부형엔 **불필요** — 흡수하지 않음 |
| select_ports (최소권한) | manifest 권한 → in-process 포트 주입 | 외부형엔 **부적용** — 외부는 자비스 메모리/포트 접근 안 함 |
| plugin_registry (탐색≠활성화) | 폴더 스캔 + enabled.json | 외부형은 *등록 대상*이 코드가 아니라 **연결 정보**(URL/결과 위치/자격증명 참조) |
| HUD 탭 마운트 | loadPlugins → panel.js 동적 로드 | 외부형도 HUD에 **카드/탭**으로 나타나야 함(공유 가능) |
| **외부 시스템 연결·제어** | **0건** | ★ 전부 신규 (보기 + 제어 채널) |

**결론**: 탑재형 인프라(복사·포트·동적 import)는 외부형에 거의 **재사용 불가**다. 외부형은
"외부 시스템을 가리키는 가벼운 레지스트리 + HUD 표시 + **리스크 비례 제어 채널**"이라는 별도
메커니즘이다.

## 3. 솔직한 통찰 — TTS는 첫 사례를 잘못 골랐다

- 현 brief의 "첫 사례 = TTS 음성 비교"는 **사실 외부 관제형**이다(음성 모델 비교 = 자비스
  기능 아닌 실험). 그런데 탑재형 아키텍처가 그걸 자비스 트리에 **흡수(B복사·in-process)** 시켰다.
- 합의 Reviewer가 경고한 *"TTS 1사례 = rule-of-three 위반(추상화가 이르다)"* 의 진짜 정체가
  이것일 수 있다 — **첫 사례가 잘못된 *종류*였다.** 탑재형 추상을 외부형 사례로 정당화했다.
- 함의: 탑재형의 "진짜 첫 사례"(계산기류 실기능)는 **아직 0개**다. 탑재형 추상의 적합성은
  여전히 미검증(rule-of-three 살아있음). 외부형은 사용자가 실제 원하는 **검증된 니즈**다.

## 3.5 관제 = 보기 + 제어 (리스크 비례 게이트) ★ 127 핵심

사용자 결정: 자비스는 외부 시스템에 대해 **전권 통제**(넓은 범위)를 갖되, 집행 게이트는
**리스크에 비례**한다. "전권"이 곧 "무제한 자율"은 아니다 — 통제된 자식 invariant 보존.

```
                  자비스 전권 통제 (넓은 범위)
                            │
            ┌───────────────┴───────────────┐
        가역적·저위험                    비가역·고위험
     (리터치·설정·재시작·재실행)       (배포·삭제·자격증명·과금)
            │                                 │
        ▶ 자율 집행                       ▶ 사람 승인 게이트
     (개입 최소화 목표)                  (통제된 자식 보존)
```

| 리스크 등급 | 예시 동작 | 게이트 | 근거 |
|---|---|---|---|
| **저 (가역)** | 외부 결과 리터치·파라미터 조정·테스트 재실행·뷰 새로고침 | **자율 집행** | `[[project_minimize_user_intervention]]` |
| **중** | 외부 시스템 시작/정지·설정 변경·브랜치 체크아웃 | 자율 or 1-클릭 확인 (사용자 튜닝) | 비례 |
| **고 (비가역/외부영향)** | 배포·삭제·자격증명 사용·외부 과금·prod 쓰기 | **사람 승인 필수** | `[[project_jarvis_controlled_child_then_friday]]` |

- **등급 분류는 *결정적 정책*으로** (LLM 판단 아님 — 동작 종류 → 등급 매핑 테이블). 계산적
  검증 우선(CLAUDE.md §2). 모호한 신규 동작만 보수적 기본값(고위험 취급) + 사람 회부.
- 제어 채널 = 자비스가 외부 시스템에 명령을 보내는 경로(HTTP API / CLI / 파일). **자격증명은
  자비스가 보유**하되 고위험 게이트가 사용을 막는다. `[[reference_claude_landlock_isolation]]` 격리 교훈 참조.

## 4. 외부형 "보기" 패턴 후보 (사용자 "둘 다" — 나란히 비교)

음성 모델 테스트를 예시로, "쉽게 본다"의 두 후보. **결정 아님 — 검토용 비교.** (제어는 §3.5 별도)

### 패턴 1 — 링크 허브 (가장 가벼움)
```
┌─ Jarvis HUD: 외부 실험 ─────┐
│ ● TTS 모델 테스트      ↗   │   클릭 → 외부 시스템/대시보드로 이동
│ ○ 이미지 생성 비교     ↗   │   자비스는 "모아둔 입구"만 제공
│ ● 캐릭터 애니메이션    ↗   │   상태 점(●live/○down)은 선택적 health ping
└────────────────────────────┘
```
- **자비스가 가진 것**: 이름 + URL + (선택) 상태 점. 결과는 외부에서 본다.
- **장점**: 거의 0 구현, 외부 시스템 완전 독립, 신뢰경계 명확(링크만).
- **단점**: 자비스 안에서 결과를 못 본다(맥락 전환). 리터치(§3.5) 얹기 어려움.

### 패턴 2 — 결과 데이터 pull / 임베드
```
┌─ Jarvis HUD: TTS 모델 테스트 결과 ─┐
│  modelA   ★★★☆   ▶🔊  latency 0.8s │   외부가 결과(JSON+샘플)를 내놓고
│  modelB   ★★★★   ▶🔊  latency 1.2s │   자비스가 읽어 HUD 안에서 렌더
│  modelC   ★★☆☆   ▶🔊  latency 0.6s │   ↳ 여기서 리터치/재실행 버튼(§3.5 저위험)
│  📊 지표 그래프    [재실행] [조정]  │
└────────────────────────────────────┘
```
- **자비스가 가진 것**: 외부 결과를 읽어 HUD에 표시 + **저위험 제어 버튼**(재실행·조정).
- **장점**: 맥락 전환 없이 자비스 안에서 결과 비교 + 리터치. "전권 관제"에 가장 부합.
- **단점**: 결과 **포맷 계약** + **제어 채널 계약** 필요(외부↔자비스 합의).

### 비교 요약

| | 패턴 1 (링크) | 패턴 2 (결과 pull/임베드) |
|---|---|---|
| 구현 무게 | 거의 0 | 결과 포맷 + 제어 채널 계약 + reader |
| 맥락 전환 | 있음(외부로 나감) | 없음(자비스 안) |
| 제어(§3.5) 얹기 | 어려움(외부에서) | **자연스러움**(HUD 내 버튼) |
| "전권 관제" 부합도 | 입구 모음 | 보기 + 제어(더 높음) |
| 공존 가능성 | **둘은 배타 아님** — 링크 기반 + 진짜 관제할 것만 패턴 2로 승격 | |

→ **권고 방향(검토용)**: 패턴 1을 바닥에 깔고(모든 외부 실험 = 최소 링크 카드), *진짜 관제/
리터치할 것*만 패턴 2 + §3.5 제어로 승격. 점진적·비례적. 전권은 *능력*으로 설계하되 사용은
리스크 게이트가 조절.

| **G5** | **제어 채널 형태(§3.5)** | HTTP API 호출 / 외부 CLI 실행 / 파일 명령 drop / 셋 혼합 |
| **G6** | **리스크 등급 매핑 소유권** | 자비스 코어 고정 테이블 / 외부형 manifest가 자기 동작 등급 선언(+코어 검증) |
| **G7** | **관제 대상 경계 식별(§1.5, 127)** | provenance 표식(자비스-origin 자동 기록) / 사람 명시 등록 게이트 / 둘 다. **fail-closed: origin 불명=대상 아님** |

## 6. 비례성 / 정직 단서

- ~~제어는 trigger 전 미도입~~ **정정(127)**: 사용자가 *전권 통제* trigger 를 명시 → 제어 도입.
  단 **리스크 비례**(§3.5)로 무게 조절. `[[feedback_proportionate_security_personal_tool]]`.
- "전권"이 곧 "자율 무제한"은 아님 — 게이트는 유지하되 **리스크에 비례**(통제된 자식 invariant
  보존, `[[project_jarvis_controlled_child_then_friday]]`). 무거운 인프라(실시간 스트리밍·자동
  브랜치 전환·자율 배포 파이프라인)는 여전히 명시 trigger 전 DEFER.
- **보안 표면 증가 경고**: 외부 시스템 write/control + 자격증명 보유는 read-only 링크보다 표면이
  크다. 자비스가 뚫리면 외부 시스템도 영향. → **풀 3+1 합의 + 보안 다중검증** 대상(CLAUDE.md
  "보안 관련 변경 = 3+1 필수"). 단축 검토 부적합.
- TTS 재분류(G3)는 **이미 동작·검증된 코드**를 건드림 — 비례성상 "그대로 두고 새 외부형은 새
  사례로"가 안전 기본값 후보(되돌림 비용 0). `[[feedback_ceremony_inflation]]`.
- **범위 한정이 게이트를 대체하지 않음(§1.5, 127)**: 외부 관제 대상을 "자비스 도움 프로젝트"로
  좁힌 건 표면 *완화*일 뿐 — 워커=통제된 자식이라 §3.5 리스크 게이트는 유지된다. **좁힘 ≠ 신뢰.**
- 이 brief는 **개념 정리**다. 코드 변경 0. 패턴/갈림길은 합의·사용자 결정 후 별도 TDD.

## 7. 다음 단계 (권고 — 자동 진입 0)

1. **사용자 검토**: taxonomy(§1) + 리스크 비례 게이트(§3.5) + 갈림길(§5)이 멘탈 모델과 맞는지.
2. **풀 3+1 합의 권고**: 외부 시스템 write/control + 자격증명 = 보안 표면 ↑ → CLAUDE.md §3
   "보안 관련 변경 = 3+1 필수". A(구현가능성/제어채널)·B(보안/게이트 견고성)·C(대안: 더 가벼운
   관제 모델) + Reviewer. 외부 LLM 1+ 는 비례성상 선택(개인 툴, prod 아님).
3. 합의 후 → 갈림길(G1~G6) 결정 → TDD.
