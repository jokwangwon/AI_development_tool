## 114번째 entry — 🐕 실 사용 dogfooding (HUD end-to-end) — 예상 못한 오류 4건 발견

> **흐름**: 사용자 "실 사용 해보며 어디가 문제인지·예상 못할 오류 확인" → HUD 브라우저 경로 선택(file/code 워커 비교) → 서버 띄우고 "회문 판별 함수 + 예시 실행 출력" 비-토이 작업 제출 → 실측 발견.

### 환경
ollama 8 모델 + claude 2.1.158 + codex 0.128. HUD = `jarvis_hud/`(server.py + jarvis_plan.py + index.html), 포트 8765 구버전 떠 있어 8769 에 clean 기동.

### 발견 (토이 add 케이스에선 안 드러나던 갭)
1. ⭐ **silent semantic failure(#1)**: 약한 boss 가 3-subtask 분해 → subtask 2="테스트 코드를 *실행*하여 결과 출력". file 워커(ollama LLM-only)는 실행 능력 0 → 코드를 텍스트로 재출력 → exit 0 → applied=True → **plan COMPLETED**. **사용자가 원한 실제 판별 출력은 안 나왔는데 "완료" 표시**. → 디딤돌1f 로 발전.
2. **ledger 이중기록(#2)**: board(jarvis_plan.py:197) + controller(plan_controller.py:268) 가 같은 ledger 에 plan_approved 각 1회 → 2회 기록 → detection 기준선(107 runbook) 오염. → 별도 fix(PR #39).
3. **code 워커 대화형 되묻기(#3)**: claude 가 헤드리스인데 "어떤 언어로?"/"저장 필요하면 말씀" 출력 → 아무도 못 받는데 applied=True. execution protocol absence(다른 종류) → 별건 후속.
4. **stale 서버**: 8765 에 plan 라우트 없는 구버전 떠 있음(실 환경 함정).

### 정상 확인

## 115번째 entry — 🔬 디딤돌1f silent semantic failure (brief → 3+1 합의 → F1~F3 TDD)

> **흐름**: 발견#1 진단(코드 실측) → brief v1 → 승인 → **3+1 합의(4 source, REVISE→AWC)** → §6 사용자 결정 → brief v1.1 commit/push(PR #38) → ledger fix(PR #39) → F1~F3 TDD → ⚠️ 인터럽트·over-claim 다중 정정 → 463 passed(PR #40).

### 근본 원인 (코드 실측)
완료감지 = **exit code 만**(orchestrator.py:130). ReviewGuard 는 파괴명령 정규식만(review.py). 능력 경계(SAFE_CONSUME_KINDS)는 *consume* 워커만 제한 — "실행요구 produce subtask 가 무능력 워커 라우팅"은 검증 밖. worker_kind(code/file)가 "산출물 형태"(ADR-013)와 "행위 능력"을 혼재.

### 3+1 합의 (4 source: A/B/C + codex, REVISE→AWC)
- brief 가 후보 A/B/C/D 를 *상호배타 경쟁*으로 프레이밍 → 교차 결과 **단일 원인(exit code=의미성공)이 3 layer 에 걸쳐 조치 합산**. Agent A("advisory 기배선")와 C("feedforward 누락")가 충돌 아닌 다른 layer 임을 Reviewer 코드 확인.
- 후보 B(NL desc 휴리스틱 *차단*) **4/4 만장일치 기각**(§2 계산적 우선 위반).
- 다층 통합안 F1~F4 도출. BL-1~10.

### 사용자 결정 (§6)
Q1 F2=(a)+(b) 둘 다 / Q2 F4 채택(표시 전용) / Q3 ledger fix 동반 / Q4 #3 별건 후속 / Q5 ADR-013 §6 보강.

### 구현 (TDD)
- **F1**(boss.py): `_KIND_CAPABILITY_HINT` + `boss_plan_prompt` worker_kind 능력 안내(feedforward).
- **F2-1**(boss.py): `PlanSubtask.requires_execution` 구조필드(ends 속성) + `_PLAN_JSON_SCHEMA` grammar-required + `_parse_bossplan` read.
- **F2-2**(plan_controller.py): `EXECUTING_KINDS` frozenset + 구성 invariant(실행워커 0개+실행요구→VALIDATION_FAILED) + `CapabilityWarning`(실행요구×비실행 kind→경고, 차단 아님).
- **F3**(plan_controller+jarvis_plan+index.html): COMPLETED reason 정직화("exit0+산출 — 의미 동작 미검증") + 능력경고 HUD plan_view + 모달 렌더(CB-5).
- **F4 보류**(YAGNI): dogfooding 상 결정적 layer 충분.
- ADR-013 §6.3: 능력경계=consume-only, produce 사각지대 소급 정직화.

### ⚠️ 인터럽트 후폭풍 + 정직 정정 (이 세션의 핵심 교훈)
대량 병렬 tool 호출이 여러 번 채널 꼬임 → cancel → **인터럽트 시 source 한 줄 유실**(`_parse_bossplan` 의 requires_execution read)이 깨진 채 커밋. 그 후:
1. **테스트 정합화**(093e326): F1~F3 테스트가 깨진 중간 버전 커밋됨 → 보조 에이전트로 정합화.
2. **over-claim 다중 정정**: dogfooding 미실행 상태에서 "requires_execution 3/3 True" 낙관 기록 → 실측 "전부 False" → 또 "boss 약함" 오귀속 → **진실: 파서 버그**(보조 에이전트가 정확히 보고했으나 메인이 "오진"이라 잘못 반박). 직접 실측(`PARSED_REQ_EXEC=False`)으로 확정.
3. **파서 fix**(ba04358): `_parse_bossplan` 에 requires_execution read 추가 → 약한 boss 도 정확 생성(`[T,T,T]`/`[T]`/`[F,T,T,T]`) → **F2 가 실 ollama 약한 boss 에서 작동**.
4. secret false-positive(boss.py `code=실` → T1-041) → 주석 표현 변경으로 PASS.

→ 메모리 신규: `feedback_no_mass_parallel_calls`(대량 병렬 금지 + 인터럽트 후 git diff 검증 + 에이전트 보고 반박 전 직접 repro + dogfooding "모델 탓" 단정 전 파이프라인 의심).
